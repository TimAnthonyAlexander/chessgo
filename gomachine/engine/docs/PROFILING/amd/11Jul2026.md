**This is the current main profile.** See `9Jul2026.md` for the previous baseline
(efs28 net `chessgo_efs28_wdl06_640`, pre-full-threats) and `7Jul2026.md` for the

Prod-representative SIMD build (`GOEXPERIMENT=simd GOAMD64=v4 go1.26.4`), the
**full-threats net** `chessgo_threats_sf_640` (prod `data/nnue/kb-mirror.bin`, on
coalla `data/nnue/ft_final.bin`, md5 `397f2e4d…`, **180 MB = 188,994,112 bytes**;
H=512, D2=16, D3=32, NB=8, **16 king-buckets + horizontal mirror**, **79,856 SF
full-threats**, **int16 threat FT**, pairwise tail 16→32, int8 tail L1, 32-key Finny

Tool: `bench nps-ft` (the **enriched** loader — NOT `bench nps`, which loads a lean

(`--cpuprofile`), `go tool pprof -top`.

## ⚠️ Methodology fix vs the 9 Jul baseline

The 9 Jul numbers (`prod(base) 537k / finny 573k`) came from **`bench nps`, which
loads a LEAN net** (`ImportBulletLeanNet`, `v12.bin` — no int8 pairwise tail, no
threat block). They are **NOT comparable** to the enriched full-threats net. To get
an honest before/after, efs28 (the enriched, coarse-9,216-threat net) was
**re-measured this session with the identical `bench nps-ft` tool** on the same box.
Trust only the same-tool, same-session deltas below.

## Headline — NPS is FLAT vs efs28 (this is NOT a speed regression)

Same tool (`bench nps-ft`), same box (coalla), same session, depth 16, FEN
`r1bqk2r/pp2bppp/2n1pn2/2pp4/3P1B2/2PBPN2/PP3PPP/RN1QK2R w KQkq - 0 8`:

| net (int16 threat-FT, prod stack) | medianNPS | Δ vs efs28 |
|---|---|---|
| efs28 enriched (coarse 9,216 threats) | **469,604** | — |
| **full-threats (79,856 threats)** | **461,362** | **−1.75%** |

int16 vs int8 threat-FT: int16 costs **3.13%** (efs28) / **1.48%** (full-threats) —
the deploy chose int16 for zero threat-FT quant loss, as documented.

**Conclusion: the 79,856-column threat FT is nearly free.** Only the ~70–112 columns
*touched* per accumulator push are scattered — the table size is irrelevant to
per-push traffic — so growing the threat block 8.7× (9,216 → 79,856) cost <2% NPS.
Whatever makes the full-threats net weaker vs external engines, **it is not
movetime/NPS.**

## ⚠️ But the tree at fixed depth is NOT flat — node count is the anomaly

The same runs, node count to reach depth 16 from the test FEN:

| net | nodes @ depth 16 (int16) | nodes @ depth 16 (int8) |
|---|---|---|
| efs28 enriched | 995,370 | 1,615,755 |
| full-threats | **2,010,186** | 831,459 |

Node-count-at-fixed-depth is **chaotic** (a tiny eval perturbation — even int16 vs
int8 — reshapes the whole tree, as the wild int8 column shows), so **one FEN proves
nothing on its own.** But it is a flag worth chasing: if the full-threats eval is
*noisier* (worse move ordering, weaker cutoffs), it explores more nodes per ply, so
at **equal movetime it reaches shallower depth than efs28 did** — a real,
self-play-invisible strength hit that NPS cannot see. **This needs a proper
measurement** (mean effective-branching-factor / depth-reached-at-100ms across a
position suite, both nets), not this single number. See `ENGINE_STRENGTH.md` and the
strength-regression analysis note.

### Reading it

- **Accumulator maintenance dominates:** `applyDiff` is **32.8% cum**; the int16 FT
  column add/sub (`addColSIMD`+`subColSIMD`) are ~23% flat combined. This is where
  the full-threats net spends — and it's the same shape as efs28, just via the int16
  kernel instead of int8 (`addColI8SIMD` was efs28's hottest at 9.44%). The int16
  move (no batchApply SIMD, gated on `int8FT`) is a wash at movetime here — see the
  NPS table.
- **`sfThreatIndex` (4.46%) is genuinely new** — computing the 79,856-space threat
  index per changed edge. It's a real but modest cost, and it is **on the hot path
  that decides eval correctness** (see the strength note): if this index disagrees
  with the trainer's, the net applies weights to the wrong features.
- **The int8 tail is cheap here** (`dotU8I8VNNI` 2.40%) because coalla has VNNI. On
  NEON the same dot is 51% scalar (`arm/11Jul2026.md`) — the arches profile very
  differently; **prod is amd64, trust this one for movetime.**

## ⚠️ Methodology fix vs the 9 Jul baseline

The 9 Jul numbers (`prod(base) 479k / finny 574k`) came from **`bench nps`, which
loads a LEAN net** (no int8 pairwise tail, no threat block) — **not comparable** to
the enriched full-threats net. efs28 (the enriched, coarse-9,216-threat net) was
**re-measured this session with the identical `bench nps-ft` tool**. Trust only the
same-tool, same-session deltas.

|---|---|---|

| **full-threats (79,856 threats)** | **213,361** | **+0.6%** |

int16 vs int8 threat-FT: on NEON int16 is even **~4–6% faster** than int8 (int8's

growth cost **nothing** in NPS — only the ~70–112 columns touched per push matter.

### Reading it

- **The whole ARM profile is the int8 tail dot** (`dotU8I8Scalar` 51%). NEON has no
  VNNI (`vpdpbusd`), so the int8 L1 dot falls back to scalar — a known ARM-dev-only
  artifact. On amd64 the same op is `dotU8I8VNNI` at **2.4%** (`amd/11Jul2026.md`).
  **Do not read the ARM eval-cost mix as prod.**
- Below the scalar-tail noise, the shape matches amd: **FT accumulator maintenance**
  (`applyDiff` 23% cum; `addColSIMD`+`subColSIMD` ~9% flat / ~22% cum via
  `ftAdd`/`ftSub`) is the real eval work. `sfThreatIndex` (1.14%) and
  `appendChangedEdges` (0.60%) — the threat feature computation — are cheap.
- **NPS parity with efs28 (+0.6%) confirms:** the full-threats regression vs external
  engines is **not** movetime. See `amd/11Jul2026.md` and the strength-regression
  analysis for where it actually comes from.

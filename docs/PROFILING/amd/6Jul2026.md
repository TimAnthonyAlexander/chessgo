Umbrella (cum, for context): `applyDelta` enriched_delta.go:298 — 25.2 cum;
`accPush`→`EnrichedStack.Push` — 50.1 cum; `buildAcc`/`buildAccHalf` (full

Eval time is dominated by accumulator maintenance: `accPush` (incremental FT
update + occasional full `buildAcc` refresh) is 50.1% cum, while the forward pass
(`accEval`/`screluDotSIMD`) is only 6.9% cum — an ~88% maintenance / ~12%
forward-pass split *within eval*, essentially the same intra-eval ratio as arm64
(≈88/12). But the whole eval block compresses against search: from arm64's ~80%
of the process down to ~57% here. The FT int8 column kernels compress hardest on
AVX-512 (arm64: int8 col add/sub ≈ half the whole process; amd64:
`addColI8SIMD`+`subColI8SIMD` only 15.5% flat, int8+int16 col add/sub together
~21.5%). Because the FT kernels shrank most, `screluDotSIMD` (6.0% flat ≈ the
whole forward pass) and the edge-diff bookkeeping
(`appendChangedEdges`/`appendAttackerEdges`/`computeDelta` + `chess.attacksFrom`
1.9% flat feeding them) take a proportionally larger share of eval than on arm64,
where raw FT memory traffic swamped everything.

functions, `TT.probe` (8.7% flat) is now the #1 self-time consumer, narrowly

meaningful search entry.

## Follow-up (2026-07-07): the maintenance % is real but NOT reducible on amd64

The eval-maintenance dominance above (`accPush` ~50% cum) invites a "cut columns-touched-per-node
via batched/fused kernels" reading. **Measured false on amd64.** An isolated amd64 kernel A/B
(new `internal/nnue/batchapply_amd64_bench_test.go`) shows the batched one-pass apply is **+10–13%
slower** than the sequential per-column path, and `perf stat` shows the kernel is **L1-resident
(LLC misses = 0) at 5.5–5.9 IPC** (Zen 4's ~6-wide ceiling) — **compute/throughput-bound, not
memory-bound.** Reducing load/store traffic optimises a non-bottleneck. So the ~88%-maintenance
share here is irreducible at the kernel level on the shipping arch; the levers are **fewer
features-per-move** (algorithmic, arch-transferable) or a better/bigger net from data — not kernel
rewrites. Full mechanism + refreshed batch/finny/splitRefresh A/B in `docs/ENGINE_STRENGTH.md`
§30.3.

## NPS lever sweep (2026-07-07) — the whole pre-retrain speed well is DRY

Working thesis going in: the eval kernels are uop-throughput-bound (near-peak IPC, L1-resident),
so *retired-instruction-count* is the wall — any uop removed from the hot path is a ~linear NPS
win. Under that lens we implemented and measured every candidate lever, eval-side and search-side.
**Result: none shipped. Every lever measured ≤0 except finny (already known, ~+1%).** The thesis was
half-right — instruction count *is* the wall — but it mispredicts *which* instructions cost, because
on Zen 4's wide OoO backend the removable ones are mostly off the critical path.

| Lever | Side | Measured (coalla, prod KB net) | Verdict |
|---|---|---|---|
| **batchApply** | eval | −6% / wash (arm64 +50% — a mirage) | dead (§30.3) |
| **partition int8/int16 features** | eval | **−2.5%** (node-identical, interleaved vs directApply) | dead |
| **BCE hoist on SIMD kernels** | eval | **−1.5% / neutral** (isolated interleaved, base won 5/6) | dead |
| **staged movegen (selection-scan)** | search | **−2.5%** (off won 5/6) | dead |
| **TT child-entry prefetch** | search | killed by the gate (not built) | dead |
| **finny** (refresh cache) | eval | **+0.4–1.1%** | the only win — unshipped |

### Why each died — the mechanisms (these generalise)

1. **The eval kernel codegen is already optimal — verified at the instruction level.** `objdump` of
   `addColI8SIMD` (binutils; `go tool objdump` mangles the EVEX encoding) shows a clean 5-op loop —
   `vmovdqu64` load acc, `vmovdqu` load int8 col, `vpmovsxbw` extend, `vpaddw`, `vmovdqu64` store —
   **no spills, no redundant moves.** `archsimd` emits exactly what hand-asm would. There is no
   below-hand-asm intrinsic fix to grab.

2. **Predicted branches and L1 loads are effectively FREE here → "pure removal" of them is neutral.**
   The kernel's per-iteration bounds-check branches + address `lea`s issue on the **integer ports**,
   in parallel with the vector work on the FP ports — off the critical path. So removing them (BCE)
   frees nothing. Confirmed two ways: BCE measured −1.5%/neutral, and the disasm shows the scalar
   overhead is on a different port cluster than the bottleneck (vector ops + the double-pumped
   512-bit load/store). *Lesson: at the retirement ceiling, only uops on the bottleneck port matter;
   Go bounds checks aren't on it.*

3. **"Trade bookkeeping for downstream savings" ALWAYS lost.** partition (−2.5%), staged movegen
   (−2.5%), and batchApply (−6%) all add a per-node/per-move preparatory pass (append/partition/index
   math) to save some later work. On a throughput-bound engine the prep uops outweigh the saved ones.
   This is the single most repeated failure mode of the session — three independent levers, same shape,
   same negative sign. The only levers with a *chance* are **pure removal** (BCE — but see #2) or
   **doing genuinely less** (fewer features → retrain; skipping work on pruned nodes → see #4).

4. **Search is branch-miss-bound, and its one free lever isn't node-neutral here.** `perf record`
   showed search stalls are branch mispredicts in `selectMove` (25.3%) and `negamax` (15.5%), NOT
   TT/LLC misses — `TT.probe` is invisible in the cache-miss profile (64 MB TT fits in the 128 MB
   L3). So **TT child-prefetch is dead** (optimises a non-bottleneck; matches the earlier −5.3 movetime
   SPRT). The natural attack — staged movegen, to skip generating/scoring/SEE-ing quiets on cut-nodes
   — hits a wall specific to this engine: **move ordering reads GLOBAL history tables** (`[piece][sq]`
   butterfly/continuation), whose values mutate as sibling subtrees search. Deferring `scoreMoves`
   past the noisy stage therefore reads *different* history than a single upfront scoring pass →
   changes move order → changes the tree (scores, not just nodes). So true staged movegen is a
   strength-altering SPRT change, **not** a free speed win. The only node-neutral slice — staging just
   the *selection scan* (scores still computed upfront) — measured **−2.5%** (the split-array prep
   costs more than the `selectMove` comparisons it saves; see #3).

5. **Assembly verdict: no cheap headroom.** The one asm lever that survives the "predicted-branches-are-
   free" filter is **full-accumulator register residency** (hold the 512-wide acc in 16 zmm across a
   move's columns, killing the per-column acc load/store). But that forces tile-outer/column-inner
   iteration which re-streams weights + adds index bookkeeping — i.e. it *is* batchApply, which already
   washed (#3). Every other asm idea (BCE removal, better instruction selection) is neutral by #1/#2.

### Bottom line

The pre-retrain NPS well is **dry** on amd64 — proven exhaustively across eval and search. The engine
runs its eval at ~95% of the machine's retirement ceiling with optimal codegen, and its search cost is
branch mispredicts that can't be cheaply removed without a strength change. **finny (~+1%) is the only
unshipped speed win on the table.** The ~280 Elo lives in the **retrain** (eval *quality* per node),
not in NPS. Stop hunting movetime micro-opts on this baseline; ship finny if you want the last ~1%, and
put the effort into data. See `docs/ENGINE_STRENGTH.md` §30.3 for the eval-kernel proof.
